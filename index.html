About the project

JevGate: Evidence Governance for RAG

Retrieve broadly. Evaluate evidence. Generate from a governed context.

A small Python library that sits between your existing retriever and your answering LLM. For each query–passage pair, the Jev decision model scores relevance, answer-bearing evidence, contradiction of the query’s premise and prompt-injection signals. Deterministic, versioned policy rules in your Python code then route and rerank passages, drop near-duplicates and fill a token budget, returning an evidence bundle with provenance, exclusions and a decision trace.

The scores are model judgments and can be wrong; the routing is ordinary code. No vector database or web framework required. Apache-2.0. The package is evidence-governor (import jevgate).

What a production chatbot saves

One million tokens is only about 350 queries, which is too small to feel. A production RAG support or knowledge chatbot typically answers 1,000 to 100,000 questions a day, so the calculator starts at 10,000. The inputs come from the tests. Each query retrieved 20 chunks of about 400 tokens. The baseline filled a 3,000-token evidence budget in rank order (2,879 tokens on average) and the governed prompt averaged 1,364 (Haiku run). Jev scored all 20 chunks with one request each, about $0.000872 per query. Prices are example list prices, not quotes; verify current ones.

Counts input tokens only. Answer length barely changes (about −3% in characters, −1% outside unanswerable questions), so no output savings are assumed. The Jev fee depends on how many chunks you score, not on prompt size: about $0.0000436 per chunk.

Plugging it in

Three steps, no migration

The evidence-governor package is a library and CLI with no web framework, database or specific retriever (it depends on pydantic, httpx and tiktoken only). It reads a list of passages and returns a ranked, token-budgeted bundle with provenance. The package is not on PyPI; install it from GitHub or a checkout.

STEP 1

Install

# from the repo root
pip install git+https://github.com/rajeevksp/jevgate.git
# or from a checkout
pip install -e .

You need an OpenRouter API key with access to the Jev model. Passage text is sent to OpenRouter, which is why allow_external_transmission=True is a required opt-in.

STEP 2

Call between retrieval and LLM

import asyncio, httpx
from jevgate.contracts import Candidate, GovernorRequest
from jevgate.evaluate import EvaluationConfig, evaluate
from jevgate.jev.client import JevClient
from jevgate.policy import DEFAULT_POLICY

chunks = [Candidate(id=c.id, text=c.text,
          original_rank=i + 1)
          for i, c in enumerate(hits)]
request = GovernorRequest(
    query=q, candidates=chunks,
    token_budget=2000,
    allow_external_transmission=True)
config = EvaluationConfig(
    max_passage_chars=24000,
    allow_truncation=True,
    conflict_budget_share=0.25,
    dedup_similarity_threshold=0.9)

async def run():
    async with httpx.AsyncClient() as http:
        jev = JevClient(http, api_key=KEY,
              model_id="typesafe/jev-1.13")
        return await evaluate(
            request, jev, DEFAULT_POLICY, config)
bundle = asyncio.run(run())

hits is whatever your retriever returns, q the user question and KEY your OpenRouter key. A CLI is included: jevgate evaluate --input request.json --output bundle.json.

STEP 3

Prompt from the bundle

items = (bundle.accepted_evidence
        + bundle.conflicting_evidence)
context = "\n\n".join(i.text for i in items)
# each item: id, text, scores,
# original_rank, final_rank, token_count
# bundle.status may be
# "insufficient_evidence": abstain

Text comes back verbatim with provenance. A shadow mode (serve the baseline, log the governed bundle) exists in the separate reference chatbot app, not in the library.

Four typed questions per passage

  • is_relevant
  • contains_answer_evidence
  • contradicts_query_premise
  • contains_prompt_injection

Rules stay in your code

Jev answers narrow facts. Thresholds and routing live in a named, versioned policy, so you can re-route a past run under a new policy with zero new Jev calls.

Every decision is traceable

Each chunk keeps its route, rule fired and scores in decision_trace. The separate reference chatbot app (a FastAPI demo outside this repository, not part of the package) adds trace pages, analytics and a JSON API.

Read this before you quote the numbers

What the tests show, and what they don't

What held up

  • Evidence-token cuts held on every question type and both generators, and generator and total costs fell for both.
  • Unanswerable questions: 87% less context and unchanged correctness (2.0 vs 2.0). Model answers there were about 22% shorter, the only place output length moved noticeably.
  • Haiku correctness 1.68 vs 1.63: 8 questions scored higher, 7 lower, 86 unchanged. A paired sign test gives p = 1.0, so this is parity, not a win.
  • Gemini correctness 1.42 vs 1.44: 13 higher, 16 lower, 72 unchanged (p = 0.71). Also parity.
  • A separate holistic grade picked governed in 10 and baseline in 15 of Haiku's questions (17 and 21 for Gemini), 76 and 63 ties. Governed won fewer questions than baseline in both models, consistent with a tie.

Where it cost something

  • Mean per-request latency rose 15–30% in the Haiku and Gemini runs, consistent with Jev scoring running before generation. A third run set with a different generator showed lower governed latency, so the effect is not settled.
  • Haiku's small average gain came from ordinary (+4 points in total) and synthesis (+2) questions and was partly offset by conflicting-source (−2) and false-premise (−1) questions. Dropping a chunk can lose a detail a multi-source answer needs.
  • Haiku conflicting-source correctness fell (1.5 → 1.3); decoy answers went from 2 to 4 of 101; 2 over-refusals.
  • Gemini hit its output cap in 41 baseline and 40 governed answers, which depresses scores for both.
  • Jev's fee is a real cost. Below about $0.58 per 1M input tokens it outweighs the savings (GPT-4o mini, Gemini Flash class). On those models use the governor only for what it checks, not to save money, and note that these tests did not measure a quality gain from it.
  • The savings are measured against a 3,000-token budget baseline, not against sending all 20 retrieved chunks (about 8,000 tokens).

One run per question, a single judge model for grading, 101 questions. Token and cost reductions are large and consistent. Quality differences are not distinguishable from noise. The Gemini version and Jev snapshot are not recorded in the result files, and the benchmark app is not in the repository.
